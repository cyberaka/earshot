## Decisions taken during the build (proposals, for the owner to confirm)

- **Port 8090** for the service: 8080 is Mint's on this machine. ML 8091, capture 8092, Postgres 5434.
- **Diarization fallback**: Community-1 is gated; until it is downloaded, diarization clusters WeSpeaker
  embeddings of 1.5 s windows over VAD speech. It picks up Community-1 automatically once cached.
- **Chunked transcription**: Whisper runs on groups of VAD speech regions (≤ 28 s), with the previous
  text as prompt. Whole-span transcription of mostly silent channel audio lost punctuation and words.
- **Live capture → ML** is a WebSocket of 16 kHz PCM frames, plus 30 s FLAC chunks on disk.
- **"Replay audio files"** is a capture source, for tests and demos without a meeting.
- **Fonts are bundled** (`@fontsource`), not fetched from Google Fonts, because of NF-1.
- Deletes use an inline two-step button instead of a browser confirm dialog.

## Not built yet / known gaps

- Conversations are segmented per recording file, not across the day's files (PRD §5.2 step 4); a
  conversation split by the recorder's file boundary stays split, and a later import does not
  re-segment an earlier file.
- `ambient_audio_retention_days` is a setting but not enforced (the working copy is per recording).
- No automated socket-blocking test for NF-1 yet; verified manually that every listener is on
  loopback and the UI makes no external requests.
- No Testcontainers integration tests or end-to-end test against a stub LLM yet (PRD §13.2).
- The headphone check reads the default output device name; a Multi-Output Device is resolved with
  `system_profiler`, which is a heuristic.
- Live mode uses the same 7B model as batch (`llm_live_model`); a 3–4B model would cut answer latency.
- Real recorder audio has not been tested: the M-1 spike is still the first thing to do with real data.

## Fix: online call on a 1-channel input (meeting 3, reported by the owner)

Starting **Online call** with "System default" (a 1-channel mic; BlackHole not installed) left a meeting
"live" with capture failing in the background: `Invalid number of channels [PaErrorCode -9998]`.
- Capture now opens the device inside the Start request and refuses a device with too few channels
  (HTTP 400 with a readable reason); the service rolls back the meeting rows, folder and live session.
- The start form checks channels before Start (including the system default), explains that BlackHole
  and an Aggregate Device are needed, and preselects a multi-channel input when one exists.
- A meeting that captured no audio is discarded on Stop instead of queuing a post-meeting pass.
- On service start, meetings still marked live are recovered: capture is stopped and what was recorded
  is processed, or the meeting is discarded if nothing was. Meeting 3 was discarded this way.
